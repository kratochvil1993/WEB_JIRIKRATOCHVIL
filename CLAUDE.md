# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Static site for Jiří Kratochvíl — web/e-shop developer and portrait photographer. Content is in Czech (`lang="cs"`). Pure HTML/CSS/JS, no framework, no build tools, no package manager. It is a **one-page homepage** (`index.html`, full scroll experience) plus **subpages** ("jak pracuji" for web, marketing and photography, contact, FAQ) that share the styles but use a much lighter script (`page.js`).

## Git workflow

Commit and push are two separate approvals — never assume one implies the other. Commit directly to `main` (no feature branches) when asked to commit, but do **not** run `git push` unless explicitly told to push (e.g. "pushni") — a push to `origin/main` triggers an immediate Netlify deploy, so it needs its own go-ahead even right after a commit was requested.

Never delete with a glob in the workspace (`rm -f *`, `cd dir && rm *`): the safety check blocks it and only the user can approve it. Write generated files into a fresh scratch directory instead, and remove tracked files by explicit name with `git rm`.

## Commands

There is no build, lint, or test tooling in this repo. To preview locally, serve the root over HTTP (opening `index.html` via `file://` breaks relative fetches/CORS for some assets):

```bash
python3 -m http.server 8000
# then open http://localhost:8000/index.html  (or /web.html, /marketing.html, …)
```

All pages load the minified `*.min.css`/`*.min.js`, not the sources — `style.min.css` everywhere, `script.min.js` on `index.html`, `page.min.js` on every subpage. After **any** edit to `script.js`, `page.js` or `style.css`, regenerate the matching minified file (requires Node, via `npx`, no local install needed):

```bash
npx terser@5 script.js --compress --mangle --comments false -o script.min.js
npx terser@5 page.js --compress --mangle --comments false -o page.min.js
npx clean-css-cli@5 -o style.min.css style.css
```

Commit the regenerated `script.min.js`/`page.min.js`/`style.min.css` along with the source change — there is no Netlify build step (see Deployment below), so the minified files are what actually ship. Forgetting this means the site keeps serving stale CSS/JS. Quick check before a commit: re-run the commands into `/tmp` and `cmp` the result with the committed `*.min.*`.

### Images

Photos in `assets/images/` are committed as-is (no build-time image pipeline). If a new/replacement photo comes in oversized for how it's actually displayed (check the CSS), downscale and recompress it before committing, e.g.:

```bash
dwebp photo.webp -o photo.png
sips -Z 1200 photo.png            # resize longest side to 1200px, keep aspect ratio
cwebp -q 82 photo.png -o photo.webp
```

Pick the resize width from where the image actually renders (2x its CSS display width covers retina): 1200 px for the `.photo-card` portraits on the homepage, 1100 px for the `foceni.html` gallery. Set the `<img>`'s `width`/`height` to the new pixel dimensions. Every `<img>` has `decoding="async"`; everything **below the fold** also has `loading="lazy"` (gallery, homepage portrait cards); the header logo and the hero photo deck on `foceni.html` are **not** lazy on purpose (lazy above the fold delays LCP). Write `alt` texts that describe the photo and never name the person — **look at each image before writing its alt** (an earlier pass mixed up photos by reading them in the wrong order).

### Testing

- Drive pages with the Playwright MCP against the local server; stop the server afterwards (`pkill -f "http.server 8000"`). Screenshots go under `.playwright-mcp/` (git-ignored).
- Emulate `prefers-reduced-motion` with `page.emulateMedia({ reducedMotion: "reduce" | "no-preference" })` — most subpage motion is skipped for reduced motion, so test both.
- `fullPage` screenshots can show lazy images as empty boxes; scroll through the page (or flip `loading` to eager) before judging a gallery.
- After a **viewport resize**, wait ~1–1.5 s before the next `goto`, otherwise it can end in `net::ERR_ABORTED` (on the homepage `script.js` even reloads the page when the width crosses 991 px, see "Testing gotcha" below).
- Forms only work for real on the deployed site (a local `http.server` can't handle POST): mock the POST with `page.route` (filter same-origin POSTs — analytics beacons are POSTs too) and check the request body.
- Verify measurements, not just looks: heights/positions via `getBoundingClientRect`, computed styles, and the "pinned panel vs. navbar" check on 1280×720 for homepage copy changes.
- **Safari/iOS chrome and other real-device behaviour can't be tested in Playwright** (status-bar / floating-bottom-bar tint, rubber-banding, coarse scroll reporting). Serve a throw-away test page from the scratchpad with `python3 -m http.server 8001 --bind 0.0.0.0` and open `http://<Mac-IP>:8001/…` on the iPhone (`ipconfig getifaddr en0`; the IP changes between sessions). That is how the Safari bar strip was solved: a page with switchable variants (`?s=…`; variants that change `<meta viewport>`/`theme-color` are written into `<head>` with `document.write`, because a `viewport-fit` changed after load isn't reliably picked up). Kill the server afterwards (`pkill -f "http.server 8001"`).
- **Measuring backgrounds** (before/after for glow tweaks — tune by numbers, not by eye): hide the content (`main,footer,nav,section,#particle-canvas{visibility:hidden !important}`), take a screenshot, draw it into a tiny canvas (`drawImage` to e.g. 4×12 or 6×12) and print the luminance per cell (`0.2126 R + 0.7152 G + 0.0722 B`). Reference at 390×844 now (homepage): mean ≈ 33–35 (desktop ≈ 38), brightest area ≈ 47–50 below the end of the edge mask, horizontal difference ≤ 5, vertical ramp without steps. A local hotspot more than ~2× its surroundings reads as a "flek"/spotlight. A real iPhone screenshot can be sampled the same way by serving it from the same origin as a blank page (otherwise the canvas is tainted).
- Sampling GSAP-driven intros: a `requestAnimationFrame` sampler registered before GSAP's ticker reads the pre-tween state (GSAP renders `from`/`fromTo` lazily on the next tick), so the first frames look "already visible" — judge timings from later frames, not from that first sample.

## Deployment

Netlify, auto-deploy from the `main` branch on GitHub. `netlify.toml` sets `publish = "."` — **the entire repo root is what gets published**, so only files meant to be public should live there (this is why `_design/` is git-ignored rather than just left in place). Security headers (`X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`) are applied to all paths via `netlify.toml`. `assets/vendor/*` and `assets/fonts/*` get a one-year immutable `Cache-Control` there — those files never change in place, so treat a library/font bump as replacing the files wholesale (new filenames for fonts), not patching them. `assets/images/*` and `assets/fav/*` are cached for a week (same filenames get swapped in place, so a replaced image or icon can take up to a week to reach returning visitors).

All asset references (`style.min.css`, `page.min.js`, `assets/…`) and links between subpages (`web.html`, `kontakt.html`, …) use relative paths — keep it that way for anything new. Links back to the homepage use `/` and `/#anchor` (all pages live at the root, so this is safe). Pages are linked **without** the `.html` extension (`web`, `kontakt`, `gdpr#cookies`, …) and so are every `<link rel="canonical">`, `og:url`, JSON-LD `url`/`@id` and the `sitemap.xml`/`sitemap-pages.xml` URLs; the files keep their names, Netlify serves `/web` from `web.html`, and `netlify.toml` 301-redirects (`force = true`) each `/<page>.html` to `/<page>` (the old `/cz/…` and `/fotografie.html` redirects point straight at the clean URLs, no chains). Only `index.html` (→ `/`) and `404.html` keep their names. Never link to `*.html` internally — it would cost a redirect hop and contradict the canonical.

## Scripts and styles

- `style.css` — single stylesheet for **all** pages; `style.min.css` is generated from it (what every page `<link>`s, committed since there's no build step; never hand-edit). It defines CSS custom properties (`--purple`, `--magenta`, `--accent2`, `--accent-ice`, `--grad-a`, `--grad-b`, `--grad-angle`, etc.) that `script.js` mutates at runtime to drive the homepage's scroll-linked background gradient. The subpage rules (`.sub-*`, `.steps`, `.principles`, `.faq`, `.photo-gallery`, `.contact-modal`, `.ai-flow`, …) are appended at the end of the file.
  - **Palette**: the site is deliberately monochrome azure — `--accent2` (button/icon/bar gradient end) equals the old `--magenta`. `--accent-ice` (a lighter tint) used to end the heading gradients but is **unused now**: the highlighted words in headings (`.gradient-text`, name kept for the ~30 HTML uses) are solid `var(--purple)` — **no gradient-to-light anywhere on the site, on purpose**; don't reintroduce it. A cyan→blue second hue was tried and rejected (clashes with the teal background); add depth with lightness, not a new hue. The numbered "Na čem mi záleží" cards use a fade-to-transparent gradient on the numerals (not outlined: `-webkit-text-stroke` draws a stray inner line on the "4" in variable Inter) — that is fine, it is not a gradient to light.
  - **Navbar capsule (all widths)**: at the top the bar is transparent with the big logo; once `.scrolled` the **`.container`** (logo + links) shrinks into a centered glass capsule — the blur/border/shadow are *not* on the bar any more (`.navbar-custom.scrolled` and `html.weak-hw .navbar-custom.scrolled` are forced transparent, no `backdrop-filter`). Desktop (≥992 px, block "Desktopový nav" in `style.css`): the glass sits on `.container` itself (880 px wide, `border-radius:999px`); a sliding bubble `.nav-pill` (JS-created, first child of `#navMenu > .d-flex`) follows the hovered/focused link and rests behind the `.active` one (visible only when scrolled — `.rest` opacity .55); each link text is wrapped in `.nl-roll > .nl-roll-in[data-t]` and rolls up on hover (clone via `::after`; `aria-label` on the link, wrapper `aria-hidden`). That JS block is **mirrored in `script.js` and `page.js`**, like `setNav`. Below 992 px the pill is `display:none` and the roll is unstyled; the mobile split of the link text (`buildNavText`) replaces the wrapper on first open anyway.
  - **Navbar active state**: the azure underline under the active item is only shown while the header is at the top; once it turns into the frosted sticky bar (`.navbar-custom.scrolled`, desktop ≥992px) the underline fades out and the active item is told apart by colour alone (full white vs. the others dimmed to 58 %) — weight is deliberately unchanged, a bolder font would resize the items and make the menu jump. The mobile menu is a fullscreen overlay (next bullet) and tells the active item apart by azure colour only, no underline.
  - **Mobile menu (fullscreen overlay, < 992 px)**: `#navMenu` is a `position:fixed; inset:0` layer in CSS — the markup is unchanged on the six pages with a toggler (`index`, `web`, `marketing`, `fotografie`, `kontakt`, `faq`). Logic is `setNav(open, instant)`, **duplicated in `script.js` and `page.js` — keep both in sync**. On first open each link's text is split into `.nl-word`/`.nl-char` spans plus a `.nl-num` (01–05); the letters fly in like the hero h1, an outlined "MENU" (`::before`) drifts behind (CSS keyframes, only with motion allowed), the hamburger turns into × (drawn with CSS: icon 28×28, bars at 7/19 px, × at 13 px). The layer **opens as a circle** that grows from the toggler (`navCircle()` → GSAP tween of `clip-path: circle(R at cx cy)`, 0.7 s open / 0.5 s close, `clearProps` at the end; letters start at 0.14 s, numbers 0.25 s, footer 0.4 s) and shrinks back into it. First open also builds a **footer** `.nav-foot` (JS, appended to `#navMenu`: hairline, "Telefon" / "E-mail" as `tel:`/`mailto:` links, Instagram + LinkedIn icon buttons (the footer's `.social-ico` circles; every page inlines the `#bi-instagram`/`#bi-linkedin` symbols); `display:none` on desktop, whole footer hidden below 560 px height; the link list has `margin-block:auto`, the layer scrolls (`overflow-y:auto`) if it ever overflows). **Closed state on mobile = the same glass capsule as desktop** (container `width:calc(100% - 24px)`, padding 5/5/5/18, glass on `.container::before`) with a round 42 px toggler whose `::before` is a conic-gradient **progress ring** driven by `--scroll-progress` (homepage: written on `:root` by `script.js`; subpages: `page.js` writes it on the toggler only). Things that bite: (1) **`backdrop-filter` on any ancestor of `#navMenu` makes that ancestor the containing block of the fixed layer** (it shrinks to it). `#navMenu` lives inside `.container`, so the bar and the container must never carry the blur — it sits on the `.container::before` pseudo (no descendants, so harmless) and fades out (`visibility` with a 0.7 s delay) under `.nav-open`. The old `.nav-open`/`.nav-closing` bar rules are still there as belt-and-braces. Test it with `hardwareConcurrency` forced to 4 **and** 8, scrolled, in a fresh tab with `Cache-Control: no-cache` (an old Playwright tab served stale CSS/JS and gave false FAILs); check that `#navMenu` measures the full viewport when scrolled; (1b) **Safari perf (iOS, reported as stutter at the end of the close)**: the layer has **no `backdrop-filter`** (flat `rgba(4,14,20,.975)`; Safari re-renders a backdrop blur every frame of a `clip-path` tween), is `overflow:hidden` (a scroller + animated clip-path glitches; `overflow-y:auto` only at ≤480 px height), is promoted for as long as it is open (`.nav-layer`: `will-change:clip-path;transform:translateZ(0)`, added in `setNav(true)`, removed when hidden), the capsule glass (`.container::before`) is never toggled while the menu opens/closes, and the outlined MENU fades out at once under `.nav-closing`. Close eases `power2.inOut` 0.45 s (a long `power3` tail on a tiny circle looks like lag). Not verifiable in Playwright — check on a device. (2) the header stays above the layer (`.brand`/toggler `z-index:2`) and is **not** moved or scaled any more (the former translate/scale-to-top-geometry hack is gone) — when scrolled the open menu shows the small 32 px logo in the capsule position, at the top the 70 px one; (3) scroll lock is `html.nav-open{overflow:hidden}` (+ `scrollbar-gutter:auto` via `html.js.nav-open`, otherwise the subpages' `html.js{scrollbar-gutter:stable}` leaves a strip), `main, footer, body > section` get `inert`, Tab is trapped (brand → toggler → links), ESC closes and focus returns to the toggler, a `matchMedia` change to ≥ 992 px closes it instantly; (4) reduced motion = no tweens, `html.weak-hw` (set by `script.js` **and** `page.js` whenever `hardwareConcurrency <= 4`, also on phones and subpages — independent of the JS `weakHardware` flag, which is desktop-only) drops the overlay's blur (rule inside the `max-width:991.98px` media block) and swaps the capsule glass for a flatter, more opaque one. On mobile the go-to-top button shows **no progress fill** (`.ring-bar{display:none}` ≤991 px, only the track remains as a border) because the toggler ring already shows it; desktop keeps the go-to-top ring (the navbar progress line is hidden there). With reduced motion `reduceMotion` is read **once at load**, so emulate it *before* navigating when testing.
  - **Mobile background (≤ 991 px) differs between the homepage and every other page** — `index.html` carries `<html class="is-home">`, the other pages (subpages, gdpr, sitemap, 404) don't:
    - **Homepage (`html.is-home`)**: glow layer + the particle dots (`#particle-canvas`, capped at 35 on mobile, unchanged) with the glow fading into the flat `--bg` colour 180 px at the top and 140 px at the bottom (the edge mask, as in the pushed version — it is what makes the translucent Safari bars blend in), `theme-color` `#0a0a0f`, `body{background:var(--bg)}` and **no background on `html`**. The colours still follow the sections (`--grad-a`/`--grad-b`). The *shape* of the glow was changed on mobile because the original read as a spotlight: `#bg-blob-a` is a full-width vertical band (peak at ~30 % of the viewport, i.e. **below** the end of the 180 px mask — a peak inside the mask ramp looks like a cap), `#bg-blob-b` is `display:none`, the blobs don't drift on mobile (`script.js` skips the x/y tweens when `isMobile`, the opacity breath stays), plus a faint azure wash on `#bg-layer`. Measured at 390×844: horizontal difference ≤ 5 luminance units, peak ≈ 47–50, mean ≈ 33–35, falling steadily towards the bottom; desktop is untouched (circles 640/768 px, drift, no mask).
    - **Other pages (`html:not(.is-home)`)**: `html` **and** `body` have the opaque `#0c1d24`, so the negative-z-index layers (`#bg-layer` −2, blobs) are painted *under* the body box and are simply not visible — the page is a flat dark teal, there are no dots (the subpages never had a canvas), and the owner reported that top/bottom in mobile Safari looks right that way ("funguje dobře") — nothing to tune there. `theme-color` is `#0c1d24` for ≤ 991 px (`media` attribute, placed before the desktop `#0a0a0f` meta) on those pages. The glow rules inside `html:not(.is-home)` in `style.css` (top-only mask, vertical-band `#bg-blob-a`, `#bg-blob-b{display:none}`, ambient wash — tuned with the luminance-grid method under "Testing") are currently **invisible** because of the opaque body; they were left in on purpose so nothing else changes. If a glow is ever wanted on the subpages again: the body must be transparent (colour only on `html` — then Safari does not tint the bars with it) **or** `html` must have no background and the colour sits on `body` (propagated to the canvas, layers stay visible). The three combinations tried: `html`+`body` both coloured = glow/dots hidden (the current state, on purpose); `html` coloured + transparent `body` = glow visible but the bar strip comes back; `body` coloured, `html` plain = glow visible, but in the LAN test (`?s=` variants on a server that injected the variants into the real pages) **none of the variants changed the strip**.
    - `.pin-graphic .blob` is `opacity:.42` + `blur(36px)` on mobile on every page (full strength was a ~3× hotspot behind the small code cards).
  - **Safari bars (iOS) — what is known**: the status bar and the floating bottom bar are tinted with a flat colour. With `body{background:#0a0a0f}` + `theme-color #0a0a0f` that was a hard-edged strip, measured `rgb(10,10,14)` ≈ 93 pt tall at the bottom and ~65 pt at the top. Changing only `theme-color`, only `body`, only `html`, or adding `viewport-fit=cover` while the glow stayed visible did **not** change the strip in the owner's tests; it is gone only when everything is one flat colour (the other-pages setup above). Untested idea: Safari 26 may take the tint from fixed-position elements at the edges — `#bg-layer` is `position:fixed; inset:0` with `background-color:var(--bg)` (`#0a0a0f`), which matches the strip colour exactly; a test page with `#bg-layer` set to the teal (`layer`/`layeronly`/`nolayer` variants) was prepared but the owner did not run it. History: an edge mask was added, removed and reverted in July (`ca4b24b`/`6584aba`/`9afd023`).
  - **Subpage CTA** (`.sub-cta`): `::before` darkens the section (dark teal gradient + 8 px blur, masked so it fades in at the top; no blur below 992 px).
- `script.js` / `script.min.js` — the single vanilla-JS IIFE for `index.html` only (never hand-edit the `.min.js`). See "Animation architecture" below.
- `page.js` / `page.min.js` — the lightweight script for **subpages only** (never hand-edit the `.min.js`). Deliberately **not** `script.js`: that one is hard-wired to index.html's sections (pins, hero scene, particle canvas) and would throw on a subpage. Needs the three vendored GSAP files before it; if GSAP is missing it removes the `js` class so nothing stays hidden. It handles: navbar blur, mobile menu, to-top ring, custom cursor, contact copy buttons + form submit + modal, FAQ accordion, and the motion layer described under "Subpage motion".

## Subpages

Template and rules shared by `web.html`, `marketing.html`, `foceni.html` (and, partly, `kontakt.html`/`faq.html`).

- **Template**: copy `web.html`, swap the copy/meta/JSON-LD, keep the sections' CSS classes (`.sub-hero`, `.sub-section`, `.steps`, `.sub-grid`, `.principles` with numbered `.principle-card`s, `.faq`, `.sub-cta`). Calm reading layout, **no pinning**: content fades in on scroll via `.reveal` (`page.js`). ### Subpage motion (`page.js`)

All `transform`/`opacity`/`clip-path`, nothing scroll-scrubbed except the hero scatter, the graphic's retreat and the ghost drift; the whole layer is skipped under `prefers-reduced-motion`, where CSS shows everything immediately (and hides the second layer of the looping graphics, `.wireframe-layer`/`.dash-layer`, so layers don't overlap).

- Hero `h1` is split into letters (`splitChars`, a port of the one in `script.js` + a guard that skips pairs that wrapped onto two lines, e.g. after the hyphen in "e-shopy") which fly together from random positions; the other hero bits (`.hero-in`) fade up after it. Timing lives in `runTitle`: mobile 0.7 s + stagger 0.016 s, desktop 0.85 s + 0.02 s (it was 1.15 s + 0.028 s and felt slow on phones); `.hero-in` delays start at 0.35 s; if the font isn't ready after 1.2 s the plain h1 is shown without the fly-in.
- `.sub-ghost` (giant outlined word behind the hero) fades in and drifts with scroll; on desktop with a mouse it is lit up around the cursor by a masked `::after` copy (`--gx/--gy` are written on the ghost only, never on `:root`).
- The hero graphic flies in, tilts with the mouse on desktop, and loops on its own — code⇄wireframe, SERP⇄dashboard (bars + counters), photo-card deck (steps every **2 s**, set in the `tlP` timeline; first step ~4.2 s after load; the step animation itself is ~0.8 s, so each photo rests ~1.2 s) — paused by a ScrollTrigger when the hero is off-screen. Two soft rings pulse behind it **once**, when it lands after page load (`.sub-pulse`, inside a `.sub-hero-gfxwrap` that `page.js` creates because `.pin-graphic` has `overflow:hidden`) — not on every loop flip, that was tried and felt noisy.
- **Scatter on scroll** (tune the `amp` object at the top of the hero block, not the structure; `amp.dist` = px of scroll until complete, eased `power2.out`, so most happens in the first ~100 px): on desktop the h1 letters drift apart/blur/fade as the hero scrolls out (scrubbed, fully reversible — created in the intro tween's `onComplete` so it never fights the entrance) and the graphic shrinks to 80 %, lifts 60 px and fades to 35 % (visibly, on purpose — a 96 % shrink went unnoticed; change `scale` in `enableTilt()` to tone it down). **Mobile** uses `startScatterMobile` (tune `ampM`): the scatter is a stateless function of scroll (0 → `ampM.dist` px) smoothed by a short `gsap.to` on a proxy (`ampM.smooth`), no `scrub`, no blur, no graphic retreat (on a phone the graphic is what you scroll to next). A two-state play/reverse tween with a tiny threshold was tried first: it blinked at the top and could stay stuck — don't use binary toggles for scroll effects on mobile.
- `h2.reveal-wipe` wipes in from the left, slowly on purpose (`wipe` object: 1.2 s, `power1.inOut` — 1 s `power3.out` felt hurried and unpleasant, 1.7 s too slow); the generic `.reveal` fade-up is 0.9 s `power2.out`, with the batch stagger capped so a jump to a section never waits longer than ~0.5 s. The clip-path is cleared after the wipe and `.is-wiped` keeps it `none` — don't rely on `clearProps` alone, the CSS start state would come back.
- `.step` numbers pop and their connector draws via the CSS vars `--pop`/`--line`; `.feature-card`s get cursor glow (`--mx/--my`) and a light tilt.
- The FAQ `<details>` open/close smoothly: `page.js` wraps everything after `<summary>` in `.faq-body` and tweens its height + opacity; `[open]` stays until the close tween ends and `.is-closing` flips the plus back immediately; with reduced motion the native instant behaviour stays and no wrapper is created. The plus in `.faq summary::after` is drawn with two gradients (a text "+" never centres in the circle); the FAQ section of the pitch subpages is centred as a block (`.sub-page #faq .sub-narrow > *{margin-left/right:auto}`, same 820 px width).
- The page background (the two blurred blobs `#bg-blob-a/b` + `#bg-gradient`) drifts **on its own, never tied to scroll** — each blob has x and y tweens of different lengths in vw/vh (a loose non-repeating path, ~±13vw/±10vh) plus a slow opacity breath, all tunable in the `drift` object. There is deliberately **no scroll-linked colour change** (unlike the homepage), no section-entry pulse (tried, removed) and no rotation of the blurred layer (costly for the GPU, barely visible). On mobile the blobs don't drift at all (see "Mobile background").
- Mobile gets the rings, the smoothed h1 scatter and (on `foceni.html`) the swipeable card deck, but no background drift, no hero-graphic retreat and no cursor light.
- **Windows next to the steps** (git log on `web.html`, campaign checklist on `marketing.html`, viewfinder on `foceni.html`): ≥ 1200 px they are sticky in the right column and advance when scroll reaches each step (`#postup-N`); below 1200 px the window sits *under* the whole step list, so every step trigger had already fired and the animation was finished before the window came into view. `stepsWithWindow(winEl, n, gap, show)` registers both paths and decides at fire time (`wideMq`): narrow = the window itself triggers a timed sequence (`gap` 0.55 / 0.6 / 1.0 s), a `now` index guards against double plays. Test both widths.
- **Hero card deck on `foceni.html`, mobile**: swipe (pointer events, `touch-action: pan-y`, a port of the homepage one; autoplay is paused via `tlP._held` and resumes after 1.5–4.5 s) and the autofocus box `.af-box` now runs on mobile too (it used to be hidden there).
- Gotchas: in the code⇄wireframe loop on `web.html` the wireframe shapes (`parts`) are hidden by a `set` at time 0 of **every** cycle, *before* the wireframe layer starts fading in, then revealed with a plain `.to` (the button ends at its CSS opacity .85) — the earlier `fromTo(..., immediateRender:false)` applied the hidden start state only 0.35 s into the layer fade, so each shape was visible, vanished in one frame and faded back in (looked like stuttering; measured as opacity 1 → ~0.05 in a single frame, repeated every cycle). To check such loops, sample `getComputedStyle().opacity` of the layer *and* its children every `requestAnimationFrame` and look for single-frame jumps of the product (layer × child). `fromTo` tweens inside a looping timeline otherwise need `immediateRender: false` or they hide their target at creation; and the `.reveal` batch uses `overwrite: "auto"` — `true` kills other tweens (steps, cards) on the same element.

## Animation architecture (script.js)

Everything is driven by GSAP + ScrollTrigger plus one custom `<canvas>` particle system. Key pieces, in the order they appear:

- **Navbar**: `.scrolled` class toggled past 40px scroll (blur/background transition, CSS-driven; the active-item styling in that state is described under "Scripts and styles").
- **Custom cursor** (`#cursor`): follows the pointer via `gsap.to`; disabled entirely on touch/coarse-pointer devices.
- **Hero typewriter**: cycles through a `roles` array into `#roleText`.
- **Scroll-linked gradient**: a `ScrollTrigger` on `document.body` lerps between color `stops` (one per section) and writes the result into the `--grad-a`/`--grad-b`/`--grad-angle` CSS vars consumed by `style.css`.
- **Hero scroll scene** (`buildHeroScroll()` + `heroPin`): on desktop the hero is pinned for its own height with `pinSpacing: false` (adds no extra scroll — `#section-web` arrives exactly where the pin ends). The h1 and the "Kontaktujte mě" contact title are split into `.split-word`/`.split-char` spans by `splitChars()` (the element gets an `aria-label` with the original text); a scrubbed timeline scatters the letters, drifts/blurs the other hero elements, flies the code graphic across the screen and fires the particle burst. Two non-obvious constraints: (1) the `heroPin` ScrollTrigger is created **synchronously** at script start — creating it after the intro made the hero stay offset by 900px when the page reloaded already scrolled; (2) the timeline itself is built only in `heroTl`'s `onComplete`, because the intro `.from()` tweens animate the same `y`/`opacity` and would clash. The timeline's smoothing is a manual `gsap.to(tl, { progress })` in `onUpdate`, not a `scrub` option. **Desktop intro** (`deskFx = !lowPower`): the h1 is hidden at script start, split after `document.fonts.ready` (fallback 1.2 s) through the memoised `getDeskChars()` — `buildHeroScroll` reuses the same letters, never split twice — and the letters fly together (0.85 s); the right-hand code graphic flies in like on the subpages (opacity/scale/rotationY/x, 1.3 s, then two pulse rings in a JS-created `.sub-hero-gfxwrap`; no mouse tilt, the scroll scene rotates it itself) and the hero code starts typing at ~1.1 s. `heroTl` gets an empty 0.7 s tween on desktop so the other elements keep their timing. `buildHeroScroll` now waits for **all three** (`heroIntroDone`, `deskTitle.done`, `deskGfx.done`, via `tryBuildHeroScroll()`); a 3.5 s safety forces completion in throttled tabs. Mobile still uses the older `heroChars` fly-in (0.9 s + 0.45 s stagger, split synchronously at script start without waiting for fonts).
- **Pinned "scrollytelling" sections** (`buildPinned()`): `#section-web`, `#section-marketing` and `#section-portrait` get pinned via `ScrollTrigger` with `pin: true`; `#section-values` is pinned separately (its pin scrubs which card is "active"). Desktop reveals go through the `epic*` helpers (`epicFrom`/`epicTo`/`epicIn`/`epicOut`), which pick a different entrance per element type (h2 clip-path wipe, eyebrow letter-spacing, blur-in paragraphs, 3D card pop, button pop); `.pin-graphic` is excluded from them and flies in on its own from the side it sits on. This is the most complex/fragile part of the file — changes to section markup must keep the `.fade-el` and `.pin-graphic` selectors intact or the reveal breaks silently. Note `.pin-graphic` itself also carries `.fade-el`, which is why `epicEls` filters it out. `epicIn`/`epicOut` use `overwrite: true`, which is only safe because they target DOM elements — never use `overwrite: true` on shared proxy objects like `heroFx` (it also kills tweens nested in the paused hero timeline).
- **Particle canvas** (`#particle-canvas`): custom rAF loop, not GSAP. `sectionConfigs` defines per-section density/speed/hue/size (and whether particles draw connecting lines); the active config swaps based on which section is vertically centered in the viewport (`updateSectionByScroll`, which reads a matching `sections` id array — keep both arrays in the same order when adding/removing sections). Each particle moves by a constant-speed **drift** (direction `a` slowly rotating) plus a damped **kick** velocity (`vx`/`vy`, ×0.985 per frame) fed by the mouse; size/hue/drift speed ease toward the new section's config via `retarget()`. `heroFx.burst` (hero scroll scene, scrubbed there and back) must **not** feed the kick velocity — it only expands the *drawn* position away from the screen centre (`burstView`, smoothed), leaving `p.x`/`p.y` untouched, so the particles are back in place when you scroll up. `pulseFx` (`pulse()`, fired on entering each section) does kick the particles for real, but each in its own **random direction** (`p.pa`, re-rolled per pulse). A radial outward push (the old behaviour) has nothing pulling the particles back: with the wrap-around band at the canvas edge they all piled up there after a few scrolls and the background went nearly empty (zeroing the velocity on wrap did not help). Before the drift was added the 0.985 damping made particles freeze after ~3s — don't remove the drift without replacing it.
- **`lowPower` flag** (`prefers-reduced-motion` or viewport ≤ 991px): disables/simplifies pinning (including the hero pin and the desktop letter-splitting scroll scene), the `epic*` reveals, `.section-ghost` titles (hidden in CSS), the `.scroll-cue`, the custom cursor, particle link-lines, and card tilt. Particles still render, but the drift is off under `prefers-reduced-motion` (they stand still) and capped at 35 on mobile. **Any animation change needs to be mirrored in both the normal and `lowPower` code paths** — mobile and reduced-motion users get a deliberately simpler experience, not just a slower one.
- **Mobile effects (`mobileFx` = `isMobile && !reduceMotion`)**: phones/tablets without reduced-motion get lightweight, **pin-free** effects, all `transform`/`opacity`/`clip-path`/`filter` on a few elements only — hero h1 letters scatter in on load (`splitChars` + `heroTl`), section `h2`s wipe in via a `clip-path` played as a **timed** tween on entry (`mobileWipe()`, instead of the one-shot fade-up, so `mobH2`/`valuesH2` are excluded from `plainEls`/`valuesPlain`) — it was scrub-linked at first and looked jerky on phones because mobile browsers report scroll position coarsely and late; the same goes for hiding: `leaveEl` may only reset an element silently once it's fully off-screen (`end: "bottom top"`); an instant reset while it's still visible (the old `bottom 12%`) showed up as elements popping out under the navbar, and scrolling back up uses a short fade (`leaveEl(el, true)`); keep anything that's a visible "reveal" time-based on mobile and only scrub subtle things (parallax, card stack) with smoothing (`scrub: 0.6–0.8`), each `.pin-graphic` parallaxes with `yPercent` only (so it doesn't fight `enterEl`/`leaveEl`, which tween `y`/`scale`/`rotate`), particles are pushed by the finger (`touchstart/move`), buttons/cards get press feedback via gsap (not CSS `:active` — GSAP keeps an inline `scale` that would override it), and the mobile menu is the fullscreen overlay described under "Scripts and styles". The "Proč já" cards are a plain vertical list on mobile (no sticky stack, see the last bullet under "Animation architecture"). Reduced-motion users skip all of this.
- **Portrait photo autoplay (mobile, `startCardAutoplay`)**: each step flies the front card up and out (it keeps the top `zIndex`), advances the others, and only once the flown-out card is invisible does it silently move to the back of the deck and fade in. Never reassign `zIndex` of cards that are visible and overlapping at the start of a transition — the old version did exactly that and the previous front photo visibly "dropped" behind the others (a flicker every tick). The pending timeline is stored on `cards._autoTl` and must be killed whenever the loop stops.
- **Testing gotcha** (homepage only — `page.js` has no such listener): `isMobile`/`lowPower` are read once at load, so a `matchMedia("(max-width: 991px)")` listener calls `location.reload()` whenever the viewport crosses 991px. When driving the page with Playwright/devtools, wait ~1.5s after resizing across that width before navigating or reloading, otherwise the two loads collide (`net::ERR_ABORTED`). Also test the "reload while already scrolled down" case — scroll restoration exercises the pin setup differently from a load at the top.
- **Contact form** (homepage): the submit/validation/success logic is the block at the end of `script.js`; the rules (Netlify attributes, identical fields in all three forms, mocked-POST testing) are in "Contact: forms and modal" above.
- **Mobile hero mini code** (`.hero-mini-code`, `d-lg-none`): replaces the desktop-only code panel on small screens; its lines "type in" via a standalone `gsap.from(width)` tween (deliberately not inside `heroTl`, whose 1.6s safety `setTimeout` would cut it short). Lines use `width: fit-content` so the typing ends exactly at the text.
- **Particles & scroll**: each frame `drawParticles` reads the scroll delta — particles shift against the scroll direction by size-dependent amounts (depth) and fast scrolling boosts the drift; disabled under `prefers-reduced-motion`. The depth shift uses `scrollShift`, an exponentially smoothed `dy` (×0.18), **not** the raw per-frame delta: scroll position is reported unevenly (e.g. only every 3rd frame), and the raw value made the dots lurch and stand still in between. The smoothing keeps the total shift identical but spreads it over frames. Keep the mouse-block variables named `mdx`/`mdy` — a `var dx, dy` inside the `forEach` callback is hoisted over the whole callback and silently shadows the outer scroll `dy` (this killed the scroll parallax for months).
- **Measuring particle distribution** (regression check after touching the particle code): expose the array by injecting `window.__P = particles;` before `function drawParticles() {` via a Playwright `page.route` on `script.min.js` (fulfil with `script.js`), then scroll down and back up several times and count particles inside the viewport / the middle 80% / the outer 5% band. Healthy: ~90–98 of 98 inside, ~55–68 in the middle, ≤25 at the edge. The failure mode is the opposite (middle ≈ 0, edge ≈ 95).
- **Scroll performance on Chrome**: `ScrollTrigger.create({ start: 0, end: "max", onUpdate })` writes six CSS custom properties on `document.documentElement` every scroll tick (`--grad-a`, `--grad-b`, `--grad-angle`, `--glow-a`, `--glow-b`, `--scroll-progress`). Custom properties inherit, so each write invalidates styles for the whole document: removing the writes cut style recalculation 444 → 121 ms and total main-thread time ~25% over 150 wheel ticks. Not changed yet (only a few elements consume these vars: `#bg-layer`, the two blobs, the navbar progress line, `.pin-graphic .blob`), but if scroll jank on Chrome comes up again, write them on those elements instead of `:root`. Other measured main-thread costs during scroll: the deferred GTM script (~as expensive as the particle loop, ~0 when idle) and ~5–6 style recalcs per tick. The particle loop, link lines, `backdrop-filter` and `filter: blur` were each switched off in A/B runs without changing the slow-frame count. A choppy Chrome that is fine in Chrome Beta / a clean profile is an extension or browser-setting problem, not the code.
- **Tooling gotchas**: the Playwright MCP's `browser_run_code_unsafe` has no `require`, so fetch `script.js` inside the `page.route` handler instead of reading it from disk; the real Chrome can't be driven by the chrome-devtools MCP here (`DevToolsActivePort` EPERM). `npx playwright install webkit` hung while unpacking (twice, ~6 min with no progress) — a real Safari check has to be done by the user on a device (serve the repo with `python3 -m http.server` and open `http://<Mac-IP>:8000` on the iPhone).
- **Removed: "Proč já" sticky stack on mobile** (Nov 2026). Cards stuck with `position: sticky` shook while scrolling on iOS Safari (not reproducible in Chromium). Bisected on a real iPhone over LAN: pure-CSS sticky without any JS is fine; the shake appears with the full `script.js` and **does not go away** with the card dimming (`filter`→overlay), `scrub` removed, `backdrop-filter`/`preserve-3d` off, navbar hidden, all blur off, particles/`:root` writes/skew/tickers/ScrollTriggers killed. It is gone only when the cards are not sticky. So the mobile cards are now a normal list (same path as reduced motion: reveal once, all `.is-active`); the `values-stack` class, CSS and scrub code were deleted. If a stack effect is ever wanted again, do it without `position: sticky` (e.g. transform-driven). **LAN testing gotcha**: Safari caches `script.js`/`style.css` by heuristics, so test variants driven by query parameters can silently run old code — serve with `Cache-Control: no-store` (a 10-line Python handler) and open each variant in a fresh tab, otherwise results contradict each other (this cost hours).
